# Disciplinary depth and activation

## Finding

The import preserved many workflow outcomes and names but compressed several specialist methods into generic three-step instructions. Those methods were not simply moved into dependencies. Some relevant agent definitions also had empty skill bindings. Both content and activation needed repair; neither a short command nor an intelligent model makes specialist context unnecessary.

This is a source/configuration finding, not proof that compression alone caused every weak product result. A read-only inspection of an active local triage pilot showed absent recorded agent runs, a reported named-adapter availability problem, and limited visual evidence. Its PRD nevertheless contained sound human-control, fallback, and assumption handling. Its local-only synthetic scope was explicitly approved; absent production integrations were not a defect. The pilot was unfinished and no completed comprehensive QA run or rendered design comparison was established.

## Restored within existing skills

| Discipline | Methods retained in the on-demand skill layer |
|---|---|
| Product | Behavior evidence versus enthusiasm; causal bottlenecks; strongest alternative and existing-workflow options; disconfirmation; outcome measures and guardrails; falsifiable requirements. |
| Design | Task and attention hierarchy; coherent typography, density, color and composition; genuinely different interaction directions; orientation and recovery; distinction between taste, usability defects and unverified visual claims. |
| Engineering | Existing-code reuse; justified boundaries; invariant ownership; input-to-outcome execution paths; delayed/duplicate/concurrent failure where relevant; vertical slices and risk-specific assertions; detection and recovery. |
| QA | Independent expected outcomes; precondition/action/result evidence; durable readback; authorization and stale-update negatives; explicit executed, failed, blocked and not-run coverage; no weakening regressions for a green verdict. |

Twelve existing skills were strengthened: `product-discovery`, `plan-product-review`, `create-prd`, `design-options`, `plan-design-review`, `design-system`, `implementation-planning`, `plan-engineering-review`, `specification-writing`, `browser-qa`, `e2e-testing`, and `webapp-testing`.

Six existing agents now declare relevant skill bindings: `product-manager`, `product-owner`, `prototype-designer`, `ux-researcher`, `system-architect`, and `end-to-end-tester`. The planner already declared its planning skill. No new agent, phase, provider, output schema, or mandatory artifact was introduced.

Feature Pro loads canonical role instructions and relevant skills before dispatch. An unavailable named adapter can be mapped transparently to a fresh general agent only under the same or stricter enforceable permissions. Missing independence or enforcement still requires a user waiver; self-review cannot be relabeled as an independent review. A design critique of supplied artifacts does not require external prototype generation.

The design phase retains its token-plan and accessibility requirements but no longer imposes a number of fonts, colors, or decorative signature elements. Character should come from coherent choices for the actual product, including deliberate familiarity when appropriate.

## Verification boundaries

Catalog, phase-budget, skill-resolution, artifact-boundary and adapter-generation tests check structural integration. They cannot certify judgment, actual runtime permission enforcement, or rendered design quality. The shared command context budget remains intact; deeper instructions load through relevant skills rather than expanding the command entry point.

The [synthetic probes](../evals/skill-quality/README.md) compare eight skill texts across four disciplines with three trials per arm. These explicit diagnostic cases are not a held-out benchmark or a full workflow test. Report a ceiling tie honestly; do not treat word count or structural test success as proof of better outcomes.

## Deployment boundary

This change updates canonical Pro Harness sources. It does not rewrite an in-progress project's artifacts, modify the historical source, or refresh live home-directory client configuration. Command/skill wrappers read canonical files; generated agent definitions embed a snapshot of bindings. Regenerate managed adapters before relying on the updated registered agent definitions, and refresh the affected client session. Generation tests use temporary output and do not activate anything.

The next meaningful validation is an approved end-to-end feature exercise: confirm actual specialist dispatch and context delivery, inspect competing rendered design directions, and verify implementation behavior. Preserve useful deliberation; remove repeated administration, not discipline-specific reasoning.

## Architecture Pro: depth without a larger workflow

The user's subsequent Feature Pro exercise met their desired quality bar. That real-use feedback is the reference for Architecture Pro, not proof that another command already performs equally well.

The Architecture Pro audit found a narrower problem: most specialist agents already had relevant skill bindings, but dispatch did not explicitly deliver the current canonical methods. Several skills listed the right topics without enough guidance for reasoning through a concrete architectural choice. The update therefore preserves the existing agents and improves activation and selected methods rather than expanding the roster.

- **Decision quality:** connect the business goal to measurable quality scenarios, show candidate component and sequence views before selection, test score sensitivity, and expose the strongest independent objection and the resulting change or rebuttal.
- **Specialist substance:** trace authority into protected effects, invariants through racing writers and mixed-version migrations, recovery through usable business state, and workloads through amplification and shared-resource ceilings. Preserve existing useful concurrency, consistency, query, and diagnostic methods.
- **Coherent delivery:** reconcile cross-lane contradictions and map material boundaries through contracts, slices, and verification. Proposed behavior and future fitness specifications remain distinct from observed or measured proof.
- **Human clarity:** use existing decision-question guidance when needed, reuse earlier diagrams, preserve credible narrowed option sets, and have the architect explain the system back rather than quiz the user's memory.

Eight existing Architecture skills were strengthened. Existing `plan-engineering-review` is explicitly routed in options and deep design; `grill-with-docs` remains conditional in intake and decision phases. No new agent, skill, phase, provider, runtime adapter, schema, or mandatory output file was added. The 13-phase mode paths, static lane profile, source containment, independent verification, human decisions, trace handling, and certification gates remain in force.

`harness-test-cases/architecture-pro-depth.test.js` checks instruction and activation regressions, not output quality. Existing behavior tests exercise resolvers, hooks, handoffs, and legal transitions. A fresh independent scenario exercise can expose contradictory guidance but is not an end-to-end run or a measured quality/latency improvement. The next user exercise remains the practical acceptance test.

This update changes canonical sources only. Current command wrappers load those sources; dispatch now explicitly supplies current role and skill instructions. It does not regenerate installed agent snapshots, rewrite active project runs, or relax a runtime's permission limits. Static lane restrictions remain binding even where the host exposes broader tools; instruction-only controls must not be described as a technical sandbox. Missing native per-agent filtering is not a new blanket gate. If approved scope requires host-enforced isolation, missing enforcement blocks that lane; missing independent execution still blocks mandatory challenge.

## Review Pro: consequential findings, not checklist volume

The Review audit found generic core review and repository-health methods, insufficient guidance for disproving candidates, and ambiguous method delivery. Several shared reviewer roles have no skill bindings, while Architecture specialists bind their own workflow governance. Review now supplies relevant current methods explicitly without importing another command's state machine, certification, or permissions.

Four existing methods were strengthened: `pre-merge-review`, `review-production-challenge`, `review-evidence-integrity`, and `repository-health`. The small Review Core/routing changes activate them under the caller's authority. Data, security, performance, capacity, and AI depth reuse existing skills only when the change triggers them.

- Trace accepted intent and before/after behavior through retained user states, affected consumers, invariants, and visible results. Deleted branches and orphaned strings are investigation clues, not automatic defects.
- Inspect whether existing assertions could detect the changed failure and which risky boundaries mocks bypass. Missing tests are evidence gaps, not proof of a product bug; a green suite is not proof of an untested outcome.
- Have fresh verifiers seek the strongest contrary evidence and distinguish regression, newly exposed baseline behavior, and unrelated pre-existing issues. Record actual execution identities without inventing schema fields or claiming a digest proves independent judgment.
- Compose credible production failures through controls, customer/resource effects, detection, containment, and recovery. Explain the release consequence, owner, and necessary next proof.

Review remains source-read-only and does not diagnose root causes, write tests, apply patches, or dispatch Debug repairs. Existing checks require side-effect inspection; browser observation does not authorize a mutating journey. Static specialists return content for orchestrator persistence. The ten phases, fast-mode cap, required report envelopes, five risk slots, source/digest authentication, trace recovery, and origin-aware Debug handoffs remain unchanged. No new agent, skill, provider, schema, runtime machinery, or mandatory artifact was added.

`harness-test-cases/review-pro-depth.test.js` checks instruction and activation contracts; the existing Review/Debug tests exercise authenticated packets and boundaries. Independent synthetic review exercises can expose missed-state, false-positive, or mock-coverage problems, but do not establish a production review's recall, precision, latency, or safety. Real changed-repository exercises remain the acceptance test. Canonical sources are updated; installed adapter snapshots and historical runs are not rewritten.

## Debug Pro: causal judgment and trustworthy repair

Debug already had a lean default and substantial on-demand causal guidance. The audit found narrower activation gaps: a challenge phase without a declared analyst route, a shared analyst importing Architecture governance, and repair reviewers without an explicitly delivered review method. The update fixes those gaps rather than expanding the workflow.

The existing `systematic-debugging` skill now explains invariant ownership, affected/unaffected comparisons, faithful reproduction reduction, falsifiable experiments, counterevidence, and mitigation versus correction. Three existing Debug references add practical depth for signal interpretation, causal experiments and repair proof. Selected phases reuse `architecture-diagnostics`, `pre-merge-review`, and `ai-product-engineering` only for the relevant task; they do not start those skills' parent workflows.

- Preserve the relevant session, state, ordering and dependency boundary when reducing a failure. A success-only mock or setup error cannot distinguish its cause.
- Trace the invariant and its enforcing owner rather than patching the frame that reported the damage. Seek a plausible rival and evidence that could change the explanation when uncertainty warrants it.
- Verify durable effects, retained user states and affected shared consumers. Separate pre-effect failure from lost acknowledgement after commit, and deterministic AI controls from probabilistic output quality.
- Use real independent invocations when claiming challenge or repair review. Supply current methods, capability restrictions and Debug-owned inputs; keep runtime identity, source fingerprint and disposition in `DEBUG_REPORT.md`, not new fields in the closed resolution packet.
- Reuse qualifying evidence across phases instead of re-running commands for phase administration. An existing permanent regression can supply RED when context and chronology still qualify; final GREEN, fresh original reproduction, broader checks and independent repair review remain mandatory.

The thirteen phases, modes, minimal outputs, trusted baseline, pre-edit eligibility, RED-before-production rule, four failure stories, data-repair authority, teardown and independent Review return remain intact. No new agent, skill, provider, schema or mandatory report was added. Only canonical sources changed; active project artifacts, historical sources and installed adapter snapshots were not rewritten.

`harness-test-cases/debug-pro-depth.test.js` checks instruction/activation regressions, while existing behavior tests exercise source identity, real Git/digest evidence and packet acceptance/rejection. Neither passing validators nor synthetic scenario reasoning proves a model found the true cause, performed a fresh review, or improved latency. Real defect exercises remain the outcome-quality test.

## Explainer Pro: a model the reader can use

Explainer already had grounded claims, a four-layer teaching structure and immutable course publication. Its gaps were in application: audience labels did not define a different teaching emphasis, early learning prompts were first specified in the final phase, and shared specialists could inherit planning/audit instructions or artifact writes outside their static profile. The update strengthens existing methods and their delivery, not the workflow machinery.

- Teach PM, ENG, STAFF and FSB audiences from the same evidence with different emphasis. FSB connects all relevant product, design, engineering, QA, security and operational aspects, including AI-specific depth when applicable, in one end-to-end course. Carry one safe illustrative input through decisions, state changes, returns and pending work; make hypothetical values and source-only predictions explicit.
- Explain the invariant, owner and consequential branch rather than translating syntax or listing files. Connect architecture, trace, state, timing and diagrams into the same model. Distinguish declared intent, implemented behavior and external assumptions.
- Correct the false equivalence between async syntax and background work. Separate immediate promise return, the awaiting caller's completion, acceptance, persistence, business completion and acknowledgement.
- Use current canonical skills in real separate author/verifier invocations. Supply required reconstruction/evidence inputs under Explainer authority, return static-specialist content for coordinator persistence, and keep provenance in existing lane notes rather than new closed-schema fields.
- Author brief prediction prompts during the learning phases; keep full comprehension work in Phase 7. Test evidenced consequences and misconceptions, not trivia. Preserve five distinct final course outcomes without requiring five repeated outcomes per small capability or mandatory chat quizzes.
- Explain actual reuse through local wrappers, shared functions and demonstrated conventions. Bound reference reading to relevant local public surfaces and tests; external implementations are not an exhaustive-reading prerequisite. Explain changes through the same before/after scenario and what remains unchanged.

All eight phases, nine skills, three existing agent roles, capability routes, four teaching layers, independent material-claim gate, non-material sampling, source fingerprinting, evidence reuse, immutable generations, transitive invalidation, local HTML safety and completion hooks remain. No new agent, provider, schema, runtime adapter or required artifact was added. Canonical Pro-harness sources are updated; historical sources, installed agent snapshots and active project artifacts are not rewritten.

`harness-test-cases/explainer-pro-depth.test.js` checks instruction and activation regressions. Existing behavior tests validate containment, source drift, independent flags, batch publication, diagrams, quiz dependencies and trace handling; they do not prove that a separate model read source or that a reader understood the explanation. Synthetic exercises can expose contradictory instruction or unsupported simplification, but a real course and learner feedback remain the quality acceptance test.

Select the broad audience with `--audience fsb`. The existing initializer normalizes it to `FSB`; policy, state and generation schemas accept it, and generated Markdown/HTML retain the audience label. Existing audiences and the PM default are unchanged. This is an additional audience value and teaching emphasis, not a new agent or workflow. Existing saved courses are not rewritten.

## Outcome Pro: evidence that improves a decision

Outcome already had substantive arithmetic, experiment, cohort, economics and evidence-isolation methods. This pass preserves them and strengthens the connection from intent through observed value to a defensible next decision.

- Test the intended mechanism and the strongest plausible rival explanation, identifying what would distinguish them instead of turning a plausible story into a cause.
- Prioritize evidence that could change the decision, weigh collection against delay/cost/privacy, and stop at disclosed nonmaterial gaps. Required missing comparative evidence still means insufficient evidence.
- For AI initiatives, reuse existing AI expertise to distinguish offline scores from completed customer tasks, compare relevant versions/cohorts, and include human correction, failures, safety and end-to-end cost/latency.
- Compare real alternatives against the same outcome and constraints, including existing capabilities when viable. Keep future avoidable costs and switching costs distinct from sunk investment; do not invent alternatives to fill a quota.
- Start useful scoped work immediately, reuse unchanged checked evidence, and deliver current canonical methods to fresh workers. Record actual identity, method delivery and challenge disposition in the existing proof note; labels do not establish independence or host isolation.

All four phases, four flat skills, one read-only analyst with separate focuses, clean original-source challenge, repository-owned output, report schema, deterministic helpers and authority boundaries remain. AI expertise is an existing optional skill, not a new agent or provider. No new runtime machinery, schema, required artifact or live configuration change was added. Structural regression tests and scenario exercises are scoped proof; a real Outcome exercise remains the quality acceptance test.

## Customer Backward Pro: disciplinary audit and decision-quality trials

The import's three smoke exercises were not equivalent to the repeated depth work above. The follow-up therefore audits all sixteen full methods and their references, runs repeated difficult decision cases, and exercises a connected recommendation with fresh independent challenge. [Evaluation scope and fixtures](../evals/customer-backward-pro/README.md) are maintainer-only, not additional runtime phases or artifacts.

Unlike the earlier compressed Feature methods, these Customer methods already contain substantial reasoning:

| Methods | Decision-relevant depth inspected |
|---|---|
| Framing, evidence audit, access | Sponsor priors versus customer evidence; rivals and discriminating observations; source families and claim-specific permitted uses; authority versus configured tools and uncertain completion. |
| Cohort design, interview design, records | Target versus accessible frame; purposive versus prevalence sampling; proxy validation, role knowledge, neutral episodes, instrument versions, question-specific denominators and correction propagation. |
| Quantitative, behavior and insight synthesis | Exposure/mix/missingness, executed arithmetic, whole-job episodes and cross-actor consequences, rational non-use, observable situational profiles and mechanism/rival/prediction chains. |
| ICP, market intelligence, economics, positioning | Current/conditional/poor/unknown fit, actual alternatives and switching constraints, attainable value versus cash and capture, non-overlapping scenarios, useful promises tied to delivered capabilities. |
| Strategy, solution validation, independent challenge | Exist/win/sustain arguments, coherent sacrifices, competitor response, distinct evidence for comprehension/adoption/payment/feasibility, discriminating studies and fair preservation of supported narrow claims. |

Two localized source issues were repaired, followed by one observed planning weakness:

- Behavior-only inline synthesis now retains elicitation and concept-exposure context. A post-pitch account can remain useful without becoming spontaneous salience or independent demand; no upstream audit phase is forced.
- Independent challenge now tests customer-choice advantage and competitive response separately. Durable defense is assessed when claimed, not demanded as a prerequisite for every useful temporary advantage.
- Two separately graded validation-study attempts both deferred finite participant/time bounds. The method now permits justified, explicitly provisional operational limits while distinguishing them from calibrated inferential thresholds, saturation claims and permission to execute. It does not impose a universal sample or time box.

The first two issues were source-level gaps/contradictions, not demonstrated universal model failures; the third was a repeated, independently graded partial result. Frozen pre-change and patched copies allow targeted diagnosis without claiming that longer text necessarily improves outcomes. No agent, phase, provider, hook, schema, installer, mandatory output or live activation was added. Existing structural tests protect routing and contracts; observed outputs and independent judgments are the evidence for these bounded research cases, not a proof of all-runtime or real-customer quality.

## Architecture Pro: supported run initialization

Architecture Pro already had run-packet validators, a `before-phase-transition` hook, and an append-only event writer. None of those helpers could create `state.json`. `resolve-architecture-root.mjs` created only a directory. Manually writing state is forbidden, so every new run was stuck before Phase 1.

`scripts/architecture-run.mjs initialize` is the supported lifecycle CLI. It creates a new run ID, schema-valid `state.json`, and a present-time `run-started` / `phase-started` trace under a contained architecture slug. Occupied roots are refused. Callers start a new slug and reverify prior artifacts as untrusted evidence; the initializer never marks imported phases complete, infers approvals, or rewrites history. See `docs/architecture-pro-lifecycle.md`.

This updates canonical harness sources. It does not rewrite in-progress project artifacts, patch plugin caches, or publish a release. Rebuild and reinstall the Claude/Codex plugin from this checkout through the supported packaging/install path before expecting installed runtimes to see the helper.
