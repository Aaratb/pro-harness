# Architecture Pro visual delivery — audit addendum

Date: 2026-09-06. Status: source audit and recommendations, not implementation or a rendered-output verdict.

## Scope and conclusion

The new user feedback is that Architecture Pro is not visual enough and must clearly distinguish what exists from what is new. Current source supports a specific explanation: **Architecture requires explanatory views, but explicitly accepts Mermaid source without rendering; its existing/proposed distinction may be satisfied in prose and has no explicit component-and-relationship change notation.** The gap is not absence of architectural reasoning or all diagram instructions.

Only canonical Architecture command/phase/method instructions, relevant validators/tests, and Explainer's current visual delivery code were inspected. No Architecture workflow, model trial, target code, renderer, browser, or native-runtime session was executed for this addendum. No generated Architecture output was visually inspected. Frozen command-parity cases/rubrics and production instructions remain unchanged; these recommendations are not retroactive scoring requirements for trials already underway.

## Concrete findings

### 1. Visual intent is present earlier than the actual rendering route

The command asks for useful intermediate architecture, not silence until completion. Options must be shown before selection. However, the formal contract attaches `architecture-explanation-diagrams` and `diagram.render` only to Phase 12; ADR-only ends at Phase 10. The earlier view requirements can therefore be met without the dedicated diagram method or a rendered artifact. This is a delivery/activation gap, not justification to postpone every visual to the walkthrough or force ADRs through extra phases. [command:13](</Users/aaratbhatnagar/Desktop/Workspace Personal/Pro-harness/commands/architecture-pro.md:13>), [contract:17](</Users/aaratbhatnagar/Desktop/Workspace Personal/Pro-harness/commands/architecture-pro/contract.json:17>), [contract:26](</Users/aaratbhatnagar/Desktop/Workspace Personal/Pro-harness/commands/architecture-pro/contract.json:26>), [contract:31](</Users/aaratbhatnagar/Desktop/Workspace Personal/Pro-harness/commands/architecture-pro/contract.json:31>).

### 2. Current/proposed separation is weaker than a readable change map

The existing method is sound about identifiers, source grounding, contracts, direction, authority, and cross-view consistency. But a paragraph saying “this is proposed” can satisfy its wording while a diagram mixes reused components with new ones. It does not require marking a changed contract between two unchanged components, or identifying an old connection that disappears. A node-only colour scheme would still miss those relationship changes. This report recommends strengthening presentation, not claiming the current source already mandates the requested notation. ### 3. Explainer has an actual rendered delivery path that Architecture does not currently wire

Explainer's publisher calls `renderExplainerDiagram` when no SVG is supplied, sanitizes the SVG, saves it, embeds it in the course, and rejects certified publication when required visuals remain unrendered. Its validator checks the actual SVG bytes are displayed in HTML, not merely cited as Mermaid source. Architecture's inspected run/handoff validators check listed artifact bytes but do not call those visual checks or require a rendered walkthrough. ## Recommended alignment — proposed, not yet implemented

### Make existing versus new explicit on components and relationships

Use the same stable inventory and existing views. Each displayed component **and relationship** should carry an understandable status, directly or through an unambiguous local key. Status and evidence confidence are separate dimensions:

| Change status | Meaning and display rule |
| --- | --- |
| `EXISTING / unchanged` | Present in the checked baseline and retained in the target design. Cite current-source evidence; do not imply runtime observation from static inspection. |
| `NEW / proposed` | Not present in the checked baseline; introduced by this option/decision. Identify the proposal/assumption, not invented source locations. |
| `CHANGED / existing → proposed` | A retained identity changes responsibility, ownership, contract, data, direction, or timing. State the specific before/after difference. Two unchanged boxes may still have a changed relationship. |
| `REMOVED / proposed removal` | Present in the baseline but absent from the target. Show it in the baseline/change view, clearly inactive in the target; do not imply deletion has already occurred. A retargeted relationship can be an old removed edge plus a new proposed edge. |

Title each view `As-built — <checked revision/scope>`, `Proposed — <option/decision>`, or `Changes — baseline → proposal`. For greenfield, show the real existing integration context separately from the proposed system. Mark inferred/unknown current relationships as such, independently of whether the design retains or changes them; an inference is not a fifth lifecycle state. Preserve conditional, asynchronous, and failure semantics rather than overloading the same dashed line to mean both “new” and “async.”

Use a visible legend plus text labels/tags and, optionally, redundant shape/stroke/colour distinctions. The distinction must survive monochrome output and not require colour perception. Label edges with their actual contract/data/action as well as change status. A small before/after pair may be clearer than a dense overlay; choose the smallest legible treatment, not a mandatory diagram count.

### Deliver rendered views where the decision is being made

- At the existing context/options/deep-design checkpoints, show the relevant rendered view with a short explanation of what changes and why. Reuse/update it in the walkthrough. Keep Mermaid as inspectable source, not the sole claimed visual deliverable.
- Clarify the authorized local rendering path using existing renderer/safety support, while preserving separate consent for external transfer. No new provider, workflow engine, universal browser prerequisite, or copied Explainer course scaffold is needed.
- Keep source evidence, graph/change semantics, rendering/safety, and actual visual inspection as separate reported checks. If rendering is unavailable, provide the useful source/model and explicitly mark the visual deliverable incomplete; do not silently equate architectural structural certification with inspected visual quality.
- If an HTML companion is later chosen, it must display the validated image rather than merely escape Mermaid. A linked/embedded local SVG beside the Architecture explanation may suffice; a new course/publishing system is not required.

### Verify the requested improvement separately from frozen trials

After an authorized implementation, add focused checks for stable node/edge status and legend preservation, safe displayed SVGs, and changed/removed relationship handling. Then inspect a representative existing-to-proposed architecture in the actual delivery surface: can the reader identify what already exists, what is new, what changes, what disappears, and which claims remain inferred, without opening Mermaid source? Check labels, arrow direction, readable density, monochrome distinctions, and any implemented navigation/enlargement behavior.

Record observed rendering and actual native method/agent delivery separately from source/fixture assertions. Preserve evidence-backed reasoning, meaningful independent challenge, current human decisions, and Architecture's own structure. This addendum makes no claim that those future checks passed or that the ongoing frozen trials already measure this new visual acceptance expectation.
