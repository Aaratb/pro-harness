# Phase 7: Tech Spec & Data Model

> Load this file only when this phase is selected or resumed.

- **Skills**: `implementation-planning`, `plan-review-orchestrator`, `library-first-engineering`, `architecture-data-model-evolution`, `right-sized-engineering`, `architecture-decision-records`, `improve-codebase-architecture`, `zoom-out`, plus the detected data-store skill: `mongodb-performance`, `firestore-performance`, `postgres-patterns`, or `clickhouse-modeling`; add `workspace-codemap-context`, `observability-by-design` and conditional `ai-product-engineering` when their triggers apply
- **Capabilities**: `diagram.render` is required for rendered data-model and dependency-graph evidence.
- **Why this phase exists**: how the system is shaped. It turns Phase 6's requirements into an approach — boundaries, responsibilities, reuse decisions, module boundaries — and into a data model that says which entities exist, how they relate, at what cardinality, and who owns each one. It **operationalizes the architecture; it does not reopen it.** Where the model resists being drawn, that is a finding for the open-questions list with a named owner, not a licence to redecide the product.
- **Codemap context is optional:** a missing codemap never blocks. Use bounded relevant source plus the approved requirements; in greenfield work, map planned modules without inventing existing source.
- **Inputs**: `eng-requirements.md`, `prd.md`, the Phase 2 Engineering Impact Lens, the validated handoff's `design/design-doc.md` and `data-model/schema-plan.md` when present, each touched repository's `.codemaps/CODEMAP.md`, optional owner-repository `.codemaps/workspace/MASTER.md`, and applicable `.codemaps/apps/<app>.md`.

**`spec.md` is the tech spec.** Build it from the approved requirements and any certified decision rather than from scratch: the approach, responsibilities, component and data-flow view, boundaries, deployment and trade-offs, each traced to a requirement, decision id or contract id. Where `tech-spec-generator` is available, use it to deepen this document and write into `.agents/features/<slug>/spec.md`; it defaults elsewhere. Without it, author `spec.md` directly — its absence lowers depth, never blocks the phase.

- **Architecture checkpoint — before detailed specs (Phase 8):** applies to backend-only work even when Phase 4 was skipped. Sketch responsibilities, component and data-flow diagram, dependencies, trust and data boundaries, deployment, and trade-offs in `spec.md`; distinguish existing from proposed, and name the uncertainties.
  - For new systems, substantial structural changes, or unresolved cross-cutting risks, recommend `/architecture-pro --design` (`--mixed` if audit is needed), explain why, and ask via the available native selector. Require explicit consent; never auto-create another task or external action. Small features explain existing-architecture fit locally.
  - If accepted, checkpoint Phase 7; pass approved requirements, constraints, design decisions, architecture questions, and the feature-root reference. Architecture Pro retains its own repository-local run and consent gates. Return through the Phase 6 intake validator; absent, invalid, or audit-only handoffs cannot certify design.
  - If declined, record the choice and assess locally with existing agents; blockers remain.
  - Independently challenge the architecture, summarize objections and disposition, show the diagram, and request approach approval. Record route, rationale, proposal reference, and approval time in `architecture_handoff_intake.checkpoint`; missing approval on resume is pending, not inferred from artifacts. Material changes reopen approval. Phase 8 waits for it.
- **Parallel agents** (single batch):
  - `system-architect` — approach, ADRs, boundaries, dependency graph and module boundaries, including cross-cutting contracts when multiple services or repositories are involved.
  - `database-engineer` — the entity model: entities, relationships, cardinality, ownership, integrity placement, and which tables or collections are new versus changed.
  - `repository-explorer` — blast-radius scan: for each requirement, enumerate every affected file, module, endpoint, event and configuration item, grounded in opened repository evidence.
- **Harden the data model with `architecture-data-model-evolution`:** inventory writers, readers, access patterns, invariants, tenant boundaries and deletion paths. Place integrity where every writer is constrained, and name the application-only invariants that can drift. Evaluate normalization against observed access patterns, not intuition. Where a certified `schema-plan.md` came through the handoff, derive from it and do not re-decide entity ownership or integrity rules.
- **Architecture-to-delivery map:** in `spec.md` and `module-map.md`, map each component to its responsibility, its interface, and the test or fitness evidence that will show it works. Reference certified decisions and reconcile deviations before the module map is approved. Visual work consumes the selected design artifact and its defining decisions; establish the first representative screen before dependent visual expansion. Phase 8 turns this map into dependency-ordered end-to-end slices in `tasks.md`.
- **Reuse-first decision gate** (`library-first-engineering`): check existing services, functions, components, utilities, clients and patterns. Suitable local reuse closes the gate with source or test evidence and a reuse / extend / extract decision; no mandatory package research or comparison matrix. Otherwise consider standard APIs, installed dependencies, then new dependencies or custom work. Verify selected external APIs against current primary docs. Installation requires authority; an unresolved implementation-critical choice blocks the module-map approval.
- **Module map:** propose `.agents/features/<slug>/module-map.md`. For each planned module, file or composable: `path -> responsibility -> est. lines -> split plan if the module is doing more than one job`. **Size is a signal, not a rule.** A long file with one coherent responsibility is fine; a 200-line file with three responsibilities is not. Where the estimate suggests a module has accumulated unrelated jobs, say so and propose a split — and state the reason either way. Never split a coherent module to satisfy a threshold, and never keep an incoherent one because it is under one.
- **Right-sizing judgement (mandatory, one line):** the problem's actual complexity, the shape of solution it warrants, and what you deliberately did not build. A new service, queue, cache or abstraction layer where a function would do is over-engineering; one table with a JSON blob for a domain with real relationships, or integrity left to application code that cannot enforce it, is under-engineering.
- **Mandatory independent challenge** before module-map approval: coordinator or `system-architect` proposes; a **fresh** `system-architect` instance challenges feasibility, reuse, boundaries, entity ownership, failure cases, security, the right-sizing line, and unnecessary complexity. Apply the bounded routing contract and preserve objections and disposition in `spec.md`. Missing agent capability is not permission to substitute self-review.
- Review the draft with `plan-review-orchestrator`; incorporate findings, reusing unchanged architecture critique.
- **Escalation (deliberation):** apply only to material disagreement remaining after bounded challenge, not merely because alternatives exist. Use `multi-model-debate-room` for a contested architectural choice and record the outcome in the ADR's Rationale. Use `stochastic-multi-agent-consensus` to rank many independent options — queue, cache, auth pattern — before writing the ADR. Use the smallest useful panel.
- **Mermaid rule**: render the data model and the dependency graph through `diagram.render`, then embed both Mermaid source and repository-local SVG references in `erd.md`. Never claim a diagram is rendered when the capability failed.

- **Output**: `.agents/features/<slug>/spec.md`, `module-map.md`, optional `adr-NNN.md`, and `erd.md` with these named sections:
  - **Living document** — a banner: derived from the Phase 6 requirements and the codemap; re-validated and corrected during Phase 9 (Build); expect revisions.
  - **Blast radius** — `file or module -> requirement it serves -> change type (new / modify / delete) -> risk (H/M/L) -> notes`.
  - **Data model** — Mermaid entity-relationship diagram plus a table of entities, relationships, cardinality and owner. New versus changed tables or collections. **Entities and their relationships only — field definitions, types, constraints and indexes are Phase 8.**
  - **Dependency graph** — Mermaid graph of what must exist before what, module boundaries, cross-repo edges, and the risky seams.
  - **Integration touchpoints** — which APIs, events or queues, external providers, feature flags and tenant scopes are in play. Naming them is this phase; defining their contracts is Phase 8.
  - **Open questions** — each with an owner. An entity with no owner or a relationship with no stated cardinality belongs here.
- **Approval gate**: present the module map and **wait for explicit user approval** before advancing to Phase 8. Record `staff_discipline.module_map_approved: true` in `state.json` only after approval, and confirm every open question has a named owner.
- **Auto-skip**: pure-docs or no-code-and-no-data changes, or `spec.md` and `erd.md` both already exist. Where the change touches no persisted entity, narrow the data model to a stated "no data-model change" rather than skipping the phase. For backend-heavy or production-data features this phase is the whole point — do not skip it.
- **Differentiation**: Phase 6 said what must be true. This phase says how the system is shaped. Phase 8 says what exactly gets built. Reference the previous rather than restating it: if you are explaining *why*, it belongs in 7; if you are naming a column type, it belongs in 8.
