# Phase 4: Design / Options

> Load this file only when this phase is selected or resumed.

- **Skills**: `design-options`, `design-system`, `multi-model-debate-room`, `stochastic-multi-agent-consensus` — consumes `competitive-research.md` from Phase 2 when the research lane ran
- **Capabilities**: `diagram.render` is required for the rendered user flow. Use `prototype.generate` when approved and available; rendering the repository's own frontend is the preferred mockup path and local HTML is the fallback. Resolve `browser.navigate`, `browser.inspect`, `browser.capture` for authorized local inspection; no new provider or installation is required. Missing rendering leaves visual quality unverified, not passed.
- **Parallel agents**:
  - a design-system + accessibility reviewer — component selection, tokens, WCAG
  - `prototype-designer` — art direction and representative prototypes; expand to multi-screen flows only where needed
  - `ux-researcher` — usability concerns + persona fit
- For backend-only changes, auto-skip with announcement.
- **This phase produces a design to approve, not code to ship.** The nearest equivalent is a Figma file: the user reads the final version, ticks it off, and that approval is what gets built. It is not the frontend. Production frontend is written in Phase 9 against the engineering specs, is reviewed as code, and will legitimately differ in structure even where it matches this design exactly. **Phase 9 re-implements from the approved design; it never lifts mockup code into the product.** Judge this artifact on whether it settles the design question, never on whether it could ship. What carries forward as binding intent and what carries none is tabulated in `docs/design-to-production.md`; every imported decision is then built and hardened to production standard, frontend through backend, with no allowance earned by its design origin.
- **Flow gate — validated user flow before any pixels**: before art direction, prototypes, or mockups, derive the end-to-end user flow from the approved Phase 3 user stories. Render it as a Mermaid flowchart through `diagram.render` covering entry points, decision branches, the success path, empty/error/permission states, and exits, and write `design/user-flow.md` holding the source plus its rendered reference. Present it and **stop for explicit user validation**; this is what the user validates the shape of the work against. Corrections revise and re-render the flow, never start mockup work. Record the validated revision in the decision memo and set `staff_discipline.user_flow_validated: true` with `user_flow_path` in `state.json`, so a resumed run reads the gate instead of re-asking. An unvalidated flow blocks the rest of this phase unless the user waives it with a recorded reason (`staff_discipline.user_flow_waived: true`).
- **Design engine**: when the `design-mini` skill is installed, use it as the producer for this phase's design work — framing, option tree, prototype, and depth — running inside these gates rather than replacing them: the flow is validated first, and this phase's independent challenge, art-direction record, and selection point still apply. Its prototype builder can run the repository's own frontend, which is what makes the real-frontend default below achievable; `prototype-designer` stays the read-only critic. If it is unavailable, fall back to `prototype-designer` for generation and record the reduced fidelity.
- **Mockup fidelity — real frontend first**: the default mockup renders from this repository's actual frontend. Locate the real surface — route, page, container components, design-system package, tokens, data shapes — and rebuild the target screen one-to-one from those components so the mockup previews what will actually ship; a dashboard change renders through the repository's dashboard code, not a lookalike. Standalone generic HTML is the fallback only when no such surface exists or it cannot be rendered. Record that choice and treat its visual fidelity as unverified, never as approved. Rendering through real components buys an accurate preview, nothing more: it is not a head start on the build, and its component structure carries no authority over the implementation.
- Surface **architecture-driving decisions** in the design memo: data ownership, integrations, AI behavior, security, latency/offline needs, and scale assumptions that shape the experience. Explain open choices to the user; carry them into Phase 5's hardening pass rather than silently choosing a stack. Keep this design-focused, not a duplicate engineering spec.
- **Mandatory independent challenge** before selecting the design: a fresh `prototype-designer` critiques design taste, separate from the proposal author; `ux-researcher` independently challenges flows, states, and user fit. Run these read-only critiques in parallel on the same options, then synthesize under the routing contract. No external generation is needed merely to critique supplied artifacts.
- **Art direction**: apply `design-options` to establish product character from real content and inspected visual references, including sound repository screens. Explain which composition, typography, density, imagery and interaction decisions serve this product, and which reference traits do not. Record the direction, defining decisions, references, contextual anti-goals and selection in the existing decision memo. Do not invent reference observations or preserve a weak baseline merely because it exists.
- **Rendered selection**: for a new visual language or material redesign, show a representative rendered screen before expanding the design; compare alternatives only where a material choice benefits, not a fixed quota of full apps. Use realistic content and relevant viewport/state constraints. Small changes reuse a current approved direction and inspect the changed portion. Present the recommendation at the existing selection point; ask about unresolved material preferences, not already-approved choices. If rendering is unavailable, show the provisional artifact and concrete limitation; only an explicit user waiver permits proceeding with unverified visual quality.
- **Design taste**: inspect the actual rendered options on typography, visual hierarchy, composition, spacing/density, color, interaction character, and distinctiveness—not just compliance. Anchor critique in specific elements and approved context; distinguish subjective taste, usability defects and fidelity. Recommend a coherent direction with rejected alternatives; do not average opinions into a generic design. Record critique/disposition in the existing memo; return material preference conflicts to the user. A functioning, accessible screen alone is not evidence of visual quality.
- **Escalation (deliberation):**
  - Only if material disagreement remains after bounded challenge—or the user explicitly requests deeper debate—use `multi-model-debate-room` on the contested directions. Comparable options alone do not trigger extra rounds.
  - Use `stochastic-multi-agent-consensus` instead when the unresolved decision benefits from independent ranking; size the panel to the uncertainty, not a fixed N=5. Preserve dissent and user-owned taste decisions.
- **Output**: `.agents/features/<slug>/design/` with the validated `user-flow.md`, real-frontend mockups (or fallback HTML prototypes) + decision memo
- **The decision memo opens with the validated user flow.** Embed the Mermaid source and its rendered reference from `user-flow.md` at the top of the memo, not a link to it. Every design decision below is a decision *about a journey*, and a reader who cannot see the journey cannot judge the decision. `user-flow.md` remains the canonical artifact the user validated; the memo carries a copy so it reads on its own.
- **Exit gate — the record is written before Phase 5 hardens anything.** The decision memo must state the selected direction, each rejected alternative and why, the independent critique and its disposition, the art-direction decisions and contextual anti-goals, and every open question carried into Phase 5. Phase 5 reconciles the prototype against the PRD, and it can only reconcile what was written down; an approval held only in the conversation is lost at the next compaction. Record `staff_discipline.design_memo_complete: true` with `design_memo_path` in `state.json`.

## Additional phase requirements

- For visual surfaces, produce a **token plan before any component code**: hierarchy, type roles, spacing/density, semantic color values, and interaction character grounded in the task and existing brand. Reuse sound tokens. Explain what should feel distinctive or deliberately familiar and why; impose no palette, font, or novelty quota.
- Quality floor regardless of aesthetic direction: the design must answer for responsive behavior at mobile/tablet/desktop, visible keyboard focus, and `prefers-reduced-motion` respected. These are design decisions the approved artifact has to show, not production implementation this phase owes.
