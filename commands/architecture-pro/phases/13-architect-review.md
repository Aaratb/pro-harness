# Phase 13 — Architect Review and Final Seal

Load `architecture-review-readiness` and produce `ARCHITECT_REVIEW.md`: a concise decision memo plus an evidence appendix.

Include the problem and constraints, credible viable options and any evidence-backed narrowing, fresh challenge and dissent, recommendation, rejected alternatives, selected choice costs, `What I'm least sure about`, boring-baseline proof, validity envelope, falsifiers, applicable failure defense, primary-source fact status, decision request, likely questions, and strongest objections. Carry the narrowed-option justification from Phase 7; never add fake options for the memo.

The Engineering Fitness Matrix covers every material lane, including query performance, recovery, approved capacity targets, security, end-to-end latency, sync and async boundaries, races, and overload when applicable. Reference existing evidence-backed immaterial dispositions instead of manufacturing rows or repeating completed analysis. Each material row includes a measurable target, current behavior, first break, separate health/attainment/confidence outcomes, typed evidence, next proof or tuning action, owner, and deadline.

Run the architect's two-minute teach-back using the existing rendered views: explain what already exists, what is new or changes, why these boundaries, one request end to end, what fails first, and how the system recovers or evolves. Keep visual delivery and inspection status explicit, including incomplete or unverified work; a sealed architecture packet is not proof of inspected visual quality. Invite corrections; this tests the explanation, not the user's memory. Incorporate material corrections through a legal state transition. Tie final approval to the agreed decisions and remaining risk, not artifact completeness alone. Final sealing requires explicit author approval, valid trace and artifacts, recomputed digests, and a valid handoff. Never use agent attribution as the defense for a decision.
