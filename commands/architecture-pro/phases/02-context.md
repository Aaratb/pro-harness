# Phase 2 — Context and As-Built Recovery

Build the smallest evidence-backed current-state packet needed by the selected mode. Recover system boundaries, entry points, components, dependencies, owners, public and internal contracts, producers and consumers, data flows, deployment surfaces, and relevant decisions.

Conditionally inventory data models and lifecycle, material queries, latency paths, diagnostic signals, capacity ceilings, backup and recovery dependencies, synchronization and asynchronous boundaries, concurrency, overload, and operability. The security owner always produces a minimal asset, actor, trust-boundary, authority, abuse-case, and data-transfer map.

Use repository code maps as orientation only and reverify decision-sensitive claims against current source. Persist only outcome-relevant redacted evidence. Mark unknown or conflicting evidence explicitly; an incomplete search cannot prove absence.

A missing code map does not block context recovery. For greenfield scope, establish the existing repository/integration constraints and mark the new system as proposed; do not invent an as-built application. Trace a representative user operation from entry through authority, state, dependencies, and returned outcome. Separate module boundaries from deployment boundaries and current behavior from intended behavior. Use the same component identifiers in later options, contracts, and diagrams.

Load `architecture-explanation-diagrams`. Show the rendered as-built/context view from this phase's existing Markdown packet and its local HTML companion, with checked scope/revision, evidence uncertainty, and the node-and-relationship legend. Greenfield shows the real integration context separately from the proposed system. This checkpoint also applies to ADR-only; keep its view scoped to the affected decision.

Present a concise as-built map, scope coverage, consumer-census tier, security focus triggers, and material unknowns. Invite corrections without a mandatory pause when current source supports the decision-sensitive baseline. If an unknown or conflict can change scope, a hard constraint, or architecture selection, ask the targeted question and hold only the dependent work. Incorporate corrections before relying on the affected claim. Do not treat silence as approval of inferred requirements, evidence gaps, or material risk.
